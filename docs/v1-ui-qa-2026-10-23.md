## Findings blocking end-to-end readiness

### P1 — ITC ledger balance is rejected by the Expense Warrior client

The Overview and Wallet pages request `/api/v1/expense-warrior/wallet/ledger-balance` and receive HTTP 502 `ITC_FINANCE_RESPONSE_INVALID`. The app therefore cannot show the authoritative ITC ledger available balance, although the separate provider-reported balance loads.

The source contract points to the zero-hold representation: ITC's `getBalance` query can return an empty hold sum as the integer string `0`; the service returns that as `active_holds`, while Expense Warrior validates money strings in exact two-decimal form (`0.00`). ITC already has a test simulating `held_amount: '0'`, but that test asserts only `available_balance` and does not assert the wire representation. Normalize the returned zero to `0.00` (without changing any balance arithmetic) and assert the complete response contract, then retest the browser balance view.

### P1 — All configurable expense-category mappings are unset

The Admin Team page loaded 36 configurable expense-category mapping selectors and all 36 are `Not mapped`. The stock/purchasing categories are intentionally excluded from OPEX mappings. Until the approved expense categories are mapped to valid ITC OPEX accounts, manager/admin approval and posting paths are not ready for use.

### P1 — No eligible staff/manager candidates or payout destinations are available

The initial candidate lookup returned no selectable staff or managers; a read-only search for `it` also returned zero candidates. The page reports no payout destinations and no manager assignments. This prevents testing staff request routing and configuring payout destinations. The result establishes what this Admin UI can currently select; it does not prove that no employee accounts exist in ITC.

### P1 — A/R is selectable while the current ITC release defers A/R

The Payment links screen offers “Delivered invoice balance” and shows the customer/invoice fields. The current ITC release contract in the shared handoff returns `COMMERCE_RECEIVABLES_DEFERRED` for delivered-invoice A/R operations. The option must be explicitly gated as unavailable until ITC ships the approved A/R release; do not create a link that cannot be collected. Revenue and customer-credit paths remain separate.

### P2 — Loopback sign-in origin is rejected

Opening the frontend as `http://127.0.0.1:5175` caused ITC to return HTTP 403 `CORS origin denied` before checking credentials. The current LAN origin `http://192.168.10.58:5175` passed CORS and sign-in. Use the LAN URL for this phone/browser preview. Add the loopback origin to the isolated local development allowlist if direct localhost testing is needed; do not loosen production CORS.

## Not exercised

- Staff request submission, category/subcategory and attachment upload, manager decision, Admin approval, bulk payout approval, and payout recovery. The current session is Admin-only and the lists contain no requests or eligible staff candidates.
- Successful payment-link creation, collection, provider authorization prompt, callback/poll reconciliation, receipt, and receipt PDF. A valid existing link was not available, and creating one would persist a capability-bearing business record.
- CSV, Excel, and PDF report generation. The UI states that exports are recorded in audit history; export buttons were not activated because that is a persistent audit write.
- Saving team assignments, phone destinations, or category mappings; these are persistent configuration writes.
- Sandbox or live provider financial operations. No collection or payout request was submitted.

## Readiness summary

The mobile Admin shell, login/logout, navigation, empty states, provider balance display, revenue account loading, and report date controls passed this smoke pass. V1 is **not yet 90% release-ready**: authoritative ledger balance, required accounting setup, eligible staff setup, the A/R release gate, and populated end-to-end role/approval/payment tests remain open. Browser evidence is limited to the local Admin session and local-staging integration; it is not online-staging or production verification.
