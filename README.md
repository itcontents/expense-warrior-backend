# expense-warrior-backend

Independently deployable Express API and PostgreSQL service for Expense Warrior. It owns request, payment-link, provider-attempt, and audit workflows in its own database. It integrates with ITC through service APIs and never connects directly to ITC's database.

## Current state

The API has health/readiness routes, validated configuration, a guarded explicit migration runner, ITC session validation, authenticated category/request submission/list/queue endpoints, and a private evidence upload/download path. Image evidence is limited to JPEG, PNG, or WebP, capped at 5 MB, stored under generated keys with restrictive permissions, and downloadable only by the requester, assigned manager, or admin. A read-only ledger/checksum comparison under the restricted `expense_warrior_app` role confirms local migrations `0001`–`0012` match source. Migration `0013_payment_link_provider_account_snapshot.sql` remains unapplied; no migration was run during this work.

Admin manager-assignment list/create/end endpoints and a team assignment screen are now present. ITC returns only active company-staff candidates; the API verifies both IDs through ITC before every assignment write and keeps effective-dated history. An assignment change affects new requests, while requests already submitted retain their snapshotted reviewer.

Manager and admin rejection decisions are persisted with audit events; repeated identical rejections replay safely. Manager approval reserves funds through the signed ITC service. Admin rejection first releases that hold through ITC and remains retryable if the outcome is unknown. Final admin payout execution, same-ID provider recovery, exact ITC consume/release verification, admin-only bulk payout, and a recovery queue are implemented in source and covered by mocked tests. Payout and collection flags remain off. The owner reports ITC migrations `134`–`135` applied; their expected objects are present in both databases, but exact migration-ledger/checksum confirmation remains incomplete. ITC migrations `136`–`139` are source-only. No provider payment or financial mutation has been attempted. An admin-only provider-balance endpoint reads Zambia PawaPay balances with a 30-second cache, explicit refresh, and stale-data indicator; it does not treat those balances as ITC ledger availability. Revenue/customer-credit collections are implemented through the ITC service; A/R collection and credit-return paths still require the unapplied ITC migrations and account-readiness review. Request and wallet reports support CSV, XLSX, and PDF.

The API listens on port `3100`. `/api/v1/ready` returns `503` until the configured Expense Warrior database is reachable. The owner reports ITC migrations `134` and `135` applied; the expected schema objects were found in `itc` and `local_staging`, but the read-only audit role could not verify both migration-ledger rows and checksums. See [the verification record](docs/itc-migration-134-135-verification-2026-10-15.md) before enabling ITC financial calls. The A/R account prerequisite is tracked separately in that record.

The local `.env` and PawaPay private signing key are ignored by this repository. Request evidence is stored as Cloudinary `authenticated` image assets under an Expense Warrior namespace. The API stores opaque asset keys and proxies image bytes only after checking the caller's request access; do not make these assets public or return Cloudinary URLs. Configure `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and `CLOUDINARY_API_SECRET` together. Production startup requires all three. The PawaPay signing public key may be committed separately if needed for callback verification; it does not replace signed-request account configuration.

The API's `DB_USER` must be a non-superuser runtime role with only the table privileges the service needs. Keep DDL credentials out of the API `.env`; the migration CLI reads them only from ignored `.env.migrations` after `CONFIRM_EXPENSE_WARRIOR_MIGRATIONS=APPLY`. Start from `.env.migrations.example` when a separately approved migration is needed. Do not add migration credentials to the API process environment.

`npm run test:postgres` runs a gated local PostgreSQL request-repository check. It requires the restricted runtime credentials and builds session-local temporary tables from the existing schema; it does not apply migrations or write persistent application rows. The test covers request creation, manager routing, attachment metadata, idempotent replay/conflict, queue scoping, and rollback. It does not replace multi-connection concurrency tests or live ITC finance verification.
