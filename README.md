# expense-warrior-backend

Independently deployable Express API and PostgreSQL service for Expense Warrior. It owns request, payment-link, provider-attempt, and audit workflows in its own database. It integrates with ITC through service APIs and never connects directly to ITC's database.

## Current state

The API has health/readiness routes, validated configuration, a guarded explicit migration runner, ITC session validation, authenticated category/request submission/list/queue endpoints, and a private evidence upload/download path. Evidence is limited to JPEG, PNG, or WebP, capped at 5 MB and 20 MP, decoded and re-encoded to remove metadata, stored as authenticated Cloudinary assets under opaque generated keys, and streamed only to the requester, assigned manager, or admin. The API never exposes Cloudinary URLs. A previous read-only ledger/checksum comparison under the restricted `expense_warrior_app` role confirmed local migrations `0001`–`0012` match source. Migrations `0013`–`0016` remain source-only; no migration was applied for this report work.

Admin manager-assignment list/create/end endpoints and a team assignment screen are now present. ITC returns only active company-staff candidates; the API verifies both IDs through ITC before every assignment write and keeps effective-dated history. An assignment change affects new requests, while requests already submitted retain their snapshotted reviewer.

Manager and admin rejection decisions are persisted with audit events; repeated identical rejections replay safely. Manager approval reserves funds through the signed ITC service. Admin rejection first releases that hold through ITC and remains retryable if the outcome is unknown. Final admin payout execution, same-ID provider recovery, exact ITC consume/release verification, admin-only bulk payout, and a recovery queue are implemented in source and covered by mocked tests. Payout and collection flags remain off. The owner manually ran ITC migrations `134`–`135`; read-only catalog checks confirm their five expected tables exist in both `itc` and `local_staging`. SQL run directly in Valentina Studio does not create migration-ledger rows: the entries are absent in `local_staging`, and the configured `itc` audit role cannot inspect its ledger. This ledger gap does not mean the schema migrations are missing. ITC has a guarded verified-adoption command that checks readiness and records the matching source checksums without reapplying DDL; it has not been run. ITC migrations `136`–`140` are source-only. No provider payment or financial mutation has been attempted. An admin-only provider-balance endpoint reads Zambia PawaPay balances with a 30-second cache, explicit refresh, and stale-data indicator; it does not treat those balances as ITC ledger availability. Revenue/customer-credit collections are implemented through the ITC service; A/R collection and credit-return paths remain gated because their ITC migrations are unverified and account 1100 is inactive/non-postable in `local_staging`. Admin exports for request activity, wallet history, and payment-link collection attempts support CSV, XLSX, and PDF; the collection report masks payer numbers to the last four digits.

Staff payout retry is implemented in Expense Warrior source for a terminally failed provider attempt whose ITC hold release is confirmed. It appends a new attempt, persists a fresh ITC reservation identity before the signed call, resumes an unknown reservation with that identity and its original actor, and submits the new provider payout ID only after a matching active hold is confirmed. Unresolved provider or release states remain locked; consume and release target the selected attempt's hold. This also requires ITC migration `140_expense_warrior_payout_retries.sql`: without it ITC rejects every second reservation and release for a request, making retry impossible. Expense Warrior migration `0015_staff_payout_retries.sql` and ITC migration 140 remain source-only; neither was applied, and target ledger/application state has not been independently verified through the approved reader. Payout and collection gates remain off. Independent-connection concurrency, target migration rollout, live signed sandbox behavior, authenticated real-session flow, and physical-phone rendering remain pre-enable checks. See [PLAN.md](PLAN.md) and the [ITC finance service contract](docs/itc-finance-service-contract.md) for the release boundary.

The API listens on port `3100`. `/api/v1/ready` returns `503` until the configured Expense Warrior database is reachable. See [the migration verification record](docs/itc-migration-134-135-verification-2026-10-15.md) and the [ITC integration guide](../../itcstore-backend/docs/expense-warrior-integration-guide.md) for manual-SQL migration tracking and adoption. The A/R account prerequisite is tracked separately in the verification record.

Cookie-authenticated state-changing requests require an exact trusted `Origin`. Development allows localhost and LAN preview origins on port `5175`. Production must set `EXPENSE_WARRIOR_BROWSER_ORIGINS` to a comma-separated list of exact HTTPS origins without paths; startup fails if the list is missing or invalid. This protects browser writes, including final payout approval, from cross-site form submissions.

The local `.env` and PawaPay private signing key are ignored by this repository. Request evidence is stored as Cloudinary `authenticated` image assets under an Expense Warrior namespace. The API stores opaque asset keys and proxies image bytes only after checking the caller's request access; do not make these assets public or return Cloudinary URLs. Configure `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and `CLOUDINARY_API_SECRET` together. Production startup requires all three. The PawaPay signing public key may be committed separately if needed for callback verification; it does not replace signed-request account configuration.

See [Provider add-on guide](docs/provider-addons.md) before adding another mobile-money or payment provider. Provider adapters use a normalized operation contract and keep their provider and network identifiers on each attempt.

The API's `DB_USER` must be a non-superuser runtime role with only the table privileges the service needs. Keep DDL credentials out of the API `.env`; the migration CLI reads them only from ignored `.env.migrations` after `CONFIRM_EXPENSE_WARRIOR_MIGRATIONS=APPLY`. Start from `.env.migrations.example` when a separately approved migration is needed. Do not add migration credentials to the API process environment.

`npm run test:postgres` runs gated local PostgreSQL checks for request, approval/payout, and payment-link repositories. They assert the dedicated `expense_warrior` database, restricted non-superuser `expense_warrior_app` role, and session-local temporary-table resolution. The payment-link check mirrors migration 0013's source-only provider-account columns; the payout check mirrors migration 0015's retry constraints on empty temporary tables. The checks do not apply migrations or write persistent application rows. They cover request routing and idempotency, manager hold-confirmation and admin payout preparation, retry identity/replay and one-active-attempt constraints, reusable link attempts, provider-account snapshots, verified-success persistence, and closing active A/R links after settlement. They do not replace independent-connection concurrency tests or live ITC finance verification.
